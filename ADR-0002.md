# ADR-0002: One multi-tenant service, portable across clouds

- **Status:** accepted
- **Date:** 2026-11-07

## Decision

The OpenEntitlement service always runs multi-tenant. One installation hosts any number of Tenants, and each Tenant's catalog, plans, Organizations, contracts, API keys, and audit records are isolated from every other Tenant. There is no single-tenant mode: the hosted service and a self-hosted installation run the same code, and a self-hoster who wants one Tenant creates one.

People sign in through OpenID Connect. The hosted service uses Google. A self-hoster configures any OIDC provider and decides who may sign up, for example by allowed email domains. The shared admin token and evaluation token are removed. Applications authenticate with per-Tenant API keys, and console users with their sign-in session.

The service depends only on portable interfaces: a container, a Postgres connection string, an S3-compatible object store, OIDC, and optionally Stripe. No cloud identity product or proprietary database is in the code path. The first hosted deployment is AWS serverless (Lambda, Aurora Serverless v2, S3), managed by Terraform. Self-hosters use a Helm chart with their own Postgres and object store.

## Consequences

Every query is scoped to a Tenant, enforced in the application and again by Postgres row-level security. A quick local run needs an OIDC provider, so the Docker Compose examples bundle a development one. Removing the token modes is a breaking change to the service before 1.0. The SDKs and OEREP stay unchanged apart from sending an API key.

Without Stripe keys, billing is switched off and every Tenant is unrestricted. With Stripe, the service enforces its own plans on Tenants using OpenEntitlement itself.
